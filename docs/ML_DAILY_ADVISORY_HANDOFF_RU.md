# Ежедневный ML-расчёт и рекомендации: дополнение к пакету v1

Статус: код ML для интеграции; существующий `LCT_ML_backend_v1`, `ACTIVE.json` и оба frozen bundle не заменены.
Новый режим модели не вводится. Backend продолжает вызывать `MLRuntime.score_day(...)`.

## 1. Что получает backend

В каждой строке `gas` и `incidents` ответа runtime добавлено поле `recommendation`:

```json
{
  "version": "manual-advisory-v1",
  "code": "CHECK_MAINTENANCE_LOG",
  "text_ru": "Проверить журнал работ и последние показания: недавняя пауза датчиков не подтверждает поверку.",
  "basis_codes": ["GAS_PROXY", "POSSIBLE_RECENT_SILENCE"],
  "automated_action_allowed": false
}
```

Поле добавляется к прежнему ответу; `score`, `decision_status`, `reason_codes`, окна прогноза и идентификаторы не меняются.
Backend может показывать текст только у выбранных им строк (например, после своей политики top-25/cooldown). Текст не
меняет приоритет тревоги, не создаёт заявку, не отправляет уведомление и не подтверждает поверку или инцидент.

| Условие | `code` | Смысл для диспетчера |
|---|---|---|
| Газ уже ≥ 1 % в D, прогноз `abstain` | `CURRENT_ALARM_PROTOCOL` | Работать с текущей тревогой по действующему регламенту; прогноз не применяется. |
| Нет показания газа на D | `CHECK_TELEMETRY` | Проверить поступление данных и канал. |
| Иной `abstain` | `NO_GAS_FORECAST` | Посмотреть `reason_codes`, не показывать score как действительный. |
| Есть подтверждённое окно ППР | `REVIEW_VERIFIED_PPR` | Сверить окно с текущими показаниями; тревогу не скрывать. |
| После ограниченной паузы показаний | `CHECK_MAINTENANCE_LOG` | Проверить реальный журнал работ; пауза сама по себе не доказывает поверку. |
| Остальной газовый proxy-score | `REVIEW_GAS_TREND` | Если строка показана, вручную проверить динамику и текущие тревоги. |
| Инцидент на заглушке | `DEMO_ONLY` | Не использовать для оперативного решения. |
| Инцидент без прогноза | `NO_INCIDENT_FORECAST` | Проверить `abstain_reason`; score отсутствует. |

Рекомендации намеренно не зависят от нового порога score: такой порог не валидирован. Это версия текстовых подсказок,
а не ещё одна модель. Реальные рекомендации по пожару, подтоплению и НСД потребуют подтверждённого реестра инцидентов
и отдельного согласования действий с заказчиком.

## 2. Автоматический расчёт

`ml/sensor_failure/daily_forecast_job.py` — одна команда для **одних завершённых суток D**. По умолчанию D — вчерашний
день в часовом поясе машины планировщика. Для воспроизводимости лучше явно передавать `--as-of-date`.

```powershell
python ml/sensor_failure/daily_forecast_job.py `
  --journal C:\private\ext-journal-2025.parquet `
  --journal C:\private\ext-journal-2026.parquet `
  --catalogue C:\private\справочник_каналов_датчиков.csv `
  --bundles-dir C:\private\LCT_ML_backend_v1\bundles `
  --output-dir C:\private\forecast_journal `
  --as-of-date 2026-09-25 `
  --ready-marker C:\private\ready_2026-09-25.txt
```

Файл `ready_YYYY-MM-DD.txt` содержит ровно дату D и появляется **после** закрытия и проверки входного журнала. Backend
или эксплуатационная команда ставит эту команду в свой планировщик после ETL; UI и БД здесь не меняются. Для повторной
обработки исправленных входов указывается `--revision 2` — прежний результат остаётся.

Результат — `forecast_YYYY-MM-DD_rN.json`: дата, версия задания, отпечаток входных файлов, счётчики и полный ответ
`score_day` с рекомендациями. Это файл передачи backend, а не публичный отчёт: он содержит реальные ID каналов и объектов,
поэтому хранится в закрытой папке, не публикуется в Git и не выводится в консоль. По умолчанию путь
`data/forecast_journal` игнорируется Git.

Гарантии задания:

- одинаковый повтор возвращает `already_written`, без второго расчёта;
- изменённые входы для той же даты и ревизии отвергаются; новая ревизия сохраняет старый файл;
- одновременный запуск той же даты/ревизии блокируется lock-файлом;
- результат появляется атомарно только после успешного `score_day` и повторной проверки файлов источника;
- отсутствие ready-marker для D, неполный день, пустой ответ или ошибка runtime не создают файл прогноза;
- в stdout выводятся только статус, путь и числа строк, без идентификаторов.

Отпечаток проверяет путь, размер и времена изменения/создания входов. Для криптографического подтверждения полного
содержимого больших журналов backend может дополнительно передавать свой подписанный manifest ETL; в текущем задании
это не утверждается. Планировщик, хранение в БД, выбор top-25/cooldown и отображение остаются на стороне backend.

## 3. Приёмка интеграции

1. Передать backend обновлённый `lct_ml_runtime.py` и команду расчёта вместе с неизменёнными bundle ZIP и `.sha256`.
2. Проверить на их закрытом контуре один завершённый день: `as_of_date`, число строк, `recommendation.version`,
   наличие файла и повтор `already_written`.
3. Backend сохраняет `request_id`, `model_version`, `evidence_level`, `decision_status`, `recommendation` и источник
   данных. Никакое поле `recommendation` не запускает автоматическую заявку или тревогу.
4. После подключения расписания проверить отсутствие пропущенных дат и ошибки задания в мониторинге backend.

Пока этот закрытый сквозной прогон и расписание не проверены, автоматизация считается **готовой к интеграции**, а не
развёрнутой в production.
