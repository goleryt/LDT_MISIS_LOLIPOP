# Реестр инцидентов и модуль прогноза инцидентов: контракт для backend

Статус: контракт v1 от 2026-09-25. Код: `ml/sensor_failure/incident_head_v1.py` (обучение),
`incident_predictor_v1.py` (predictor в bundle), ноутбук `notebooks/kaggle/18_incident_head_stub_cpu.ipynb`,
тесты `tests/test_incident_head_v1.py`.

## 1. Идея

Главного по ТЗ — подтверждённых пожаров, подтоплений и НСД — в данных нет. Организаторы разрешили
заглушки для недостающих данных, если показано, что на реальных данных решение заработает.

Поэтому делаем модуль, который:
- принимает **реестр подтверждённых инцидентов** — формат ниже;
- сам строит цель «инцидент типа k на объекте в сутки D+2»;
- обучает, калибрует и проверяет её той же конструкцией, что газовая G2 (LightGBM + Platt, разбиение по времени,
  заранее заданные пороги допуска);
- выпускает bundle того же вида, что газовый: ZIP + `.sha256`, predictor без pickle.

Сейчас на вход подаётся **заглушка реестра**: `label_source = "stub"`. Когда заказчик даст реальный реестр, меняется только
файл — код, контракт и backend остаются прежними.

Газовый bundle G2 не меняется, это отдельный модуль.

## 2. Вход: реестр инцидентов

### 2.1. Файл `incident_register.csv` (или `.parquet`), UTF-8

| колонка | тип | обязательна | смысл |
|---|---|---|---|
| `ид_инцидента` | string | да | уникальный идентификатор |
| `ид_объект` | string | да* | как в справочнике каналов |
| `d_object_key` | string | да* | псевдоним объекта, как в панели 14; вместо `ид_объект` (так записана заглушка) |
| `тип_инцидента` | enum | да | `пожар`, `подтопление`, `нсд`; прочие значения игнорируются |
| `начало` | datetime ISO 8601 | да | время начала, в той же шкале времени, что журнал |
| `окончание` | datetime ISO 8601 | нет | время окончания; не используется в v1 |
| `подтверждён` | bool | да | в цель идут только `true` |
| `источник` | string | нет | акт, диспетчер, внешняя служба; **не признак**, только для аудита |

\* нужна одна из двух колонок. Псевдоним — `sha256("ldt-misis-panel-v3:" + ид_объект)[:16]`
(`event_panel_v3.pseudo_key`): backend переводит ключи заглушки в свои объекты тем же правилом.

### 2.2. Файл покрытия `incident_register_coverage.json`

```json
{"period_start": "2022-02-01", "period_end_exclusive": "2026-07-01",
 "objects": "all", "incident_types": ["пожар", "подтопление", "нсд"],
 "label_source": "register"}
```

Покрытие обязательно. Без него отсутствие записи в реестре нельзя считать отсутствием инцидента.
- `objects` — `"all"` или список `ид_объект`.
- `label_source`:
  - `register` — реальный реестр заказчика;
  - `stub` — наша заглушка.

## 3. Цель

Строка = (объект, сутки D). Признаки берутся на конец суток D, окно прогноза [D+2; D+3) — как у всех наших прогнозов,
то есть горизонт не меньше 24 ч.

Метка для каждого типа k:
- `1` — подтверждённый инцидент типа k **начался** в [D+2; D+3);
- `0` — объект и сутки D+2 входят в покрытие, инцидента типа k нет;
- `null`:
  - вне покрытия;
  - инцидент того же типа начался в [D−6; D]: он ещё идёт, это не прогноз (washout задан заранее);
  - инцидент того же типа начался в D+1: это событие до окна D+2, а не отрицательный пример. Число таких строк
    показывается в отчёте;
  - у объекта нет каналов на D.

## 4. Признаки

Признаки канала — те же v3-векторы, что для газового bundle (`build_features` на журнале до конца D).
Модуль сам агрегирует их до объекта:
- суммы и максимумы по группам типов датчиков;
- число активных каналов;
- доли каналов без связи и без питания;
- газ: максимум и число пересечений.

Группы типов заданы заранее по названию типа датчика, без взгляда на метки: пожарные (газ, дым, тепло,
температура), вода (затопление, уровень, насосы), доступ (движение, двери, люки, КД), прочие. Ноутбук печатает, какой
тип в какую группу попал. Код агрегации лежит внутри bundle, обучение импортирует его оттуда же.
Backend передаёт канальные векторы всех каналов объекта.

## 5. Обучение и дообучение

```
python ml/sensor_failure/incident_head_v1.py train --panel <выход 14> --register incident_register.csv \
    --coverage incident_register_coverage.json --out incident_head_bundle/
```

- **Разбиение по времени.** train → калибровка → проверка, последние периоды покрытия. Даты пишутся в bundle.
- **Пороги допуска для каждого типа** (заданы заранее):
  - в train не меньше 30 положительных и в калибровке не меньше 30, иначе тип получает статус `insufficient_labels`, и predictor
    для него отдаёт abstain;
  - на проверке G-модель должна обойти baseline: prevalence и правило «тревоги профильных датчиков за 7 суток».
    Не обошла — `decision_status = baseline_only`, и выдаётся score правила.
- **Отчёт.** PR-AUC и lift, Brier и ECE, top-k объектов в сутки с cooldown (precision и recall), доля unknown.
- **Кривая обучения.** Качество при 25 / 50 / 100 / 200 / всех положительных в train. Показывает, сколько
  реальных инцидентов нужно заказчику.
- **Результат.** `incident_head_bundle.zip` + `.sha256`: `model_<тип>.txt`, `bundle.json`, `predictor.py`, `SHA256SUMS.json`.
  Проверка при загрузке — как у газового bundle.

Дообучение = тот же запуск на новом реестре. По FAQ организаторов достаточно технической возможности. Автоматического
цикла нет, bundle всегда выпускается вручную.

## 6. Выход predictor

`predict(object_records, bundle)` → по одной записи на (объект, D, тип):

```json
{
  "request_id": "…",
  "ид_объект": "…",
  "as_of_date": "2026-09-21",
  "incident_type": "подтопление",
  "window_start": "2026-09-23",
  "window_end_exclusive": "2026-09-24",
  "score": 0.034,
  "score_kind": "calibrated_probability",
  "evidence_level": "E4",
  "label_source": "stub",
  "decision_status": "demo_stub",
  "operational_ready": false,
  "abstain_reason": null,
  "top_factors": [
    {"feature": "насосы: пуски за 7 сут", "direction": "up"},
    {"feature": "затопление: тревоги за 30 сут", "direction": "up"},
    {"feature": "доля каналов без связи", "direction": "up"}
  ],
  "model_version": "incident-head-v1-stub-…",
  "feature_contract_version": "event-panel-v3.0+…+object-agg-v1"
}
```

| поле | значения |
|---|---|
| `evidence_level` | `E0` — обучено на реальном подтверждённом реестре; `E4` — на заглушке (синтетика, как у сценариев 10) |
| `label_source` | `register` / `stub` |
| `decision_status` | `demo_stub` (заглушка, модель прошла пороги), `experimental_shadow` (реальный реестр, модель прошла пороги), `baseline_only` (модель не обошла правило: score = откалиброванное правило), `insufficient_labels` (abstain) |
| `score` | калиброванная вероятность начала инцидента типа k в окне; `null` при abstain |
| `abstain_reason` | `INSUFFICIENT_LABELS`, `OBJECT_NOT_COVERED`, `NO_CHANNELS_AT_D`, `ONGOING_INCIDENT` |
| `top_factors` | 3 главных вклада признаков в score объекта (SHAP из LightGBM), человекочитаемые имена, без значений сырых событий. Нужны для карточки прогноза. |

В `bundle.json` также лежат:
- `generator_version` — версия заглушки, для реального реестра `null`;
- покрытие;
- `score_meaning` — для заглушки «demo-score на искусственных метках, НЕ вероятность подтверждённого инцидента».

Backend показывает это рядом со score. `maintenance_context` backend добавляет сам, как у газа.

Проверка 2025 H2 — development-проверка: этот период проект уже просматривал. Parity правила на реальной
объектной панели подтверждается при интеграции: backend сверяет свой вызов `predict` с `acceptance` из results_18.

## 7. Правила для backend

- Если `label_source = stub`, в интерфейсе стоит явная плашка: «ДЕМО: модель обучена на заглушке реестра. Цифры
  показывают работу конвейера, а не качество на реальных инцидентах».
- Score разных типов не складываются и не усредняются с газовым score.
- Top-k объектов в сутки для каждого типа (для демо рекомендуем 10) и cooldown 72 ч применяет backend.
- Автоматических заявок нет. Черновик заявки на ТО — по кнопке диспетчера.
- Физической локации нет: показываются объект и тип.

## 8. Что сделать backend

1. Таблицы `incident_register` и `incident_register_coverage` со схемами из п. 2, плюс загрузка файла (CSV/Parquet).
2. Кнопка или команда «Переобучить»: запускает CLI из п. 5 и показывает статус по типам: `insufficient_labels`,
   `baseline_only`, `experimental_shadow`, `demo_stub`.
3. Ежедневный вызов `predict` по всем объектам; карточка прогноза с `top_factors`.
4. Для демо мы отдаём готовые файлы:
   - `incident_register_stub.csv` и `incident_register_coverage_stub.json`;
   - `incident_head_bundle.zip` + `.sha256`, обученный на заглушке.

## 9. Как устроена заглушка (честно)

- **Кто «случается».** Инциденты разыгрываются по реальным суткам журнала. Шанс зависит от того, насколько сильно в **сами
  сутки инцидента** сработали профильные датчики объекта:
  - пожар — газ, дым, температура;
  - подтопление — затопление, насосы;
  - НСД — движение, двери, люки.

  Плюс доля инцидентов вообще без следа в датчиках.
- **Почему это честная проверка.** Модель видит только данные до конца D, а «след» — в D+2. Поэтому проверяется, можно ли
  **заранее** предсказать всплеск профильной активности, а не угадать рецепт генератора.
- **Четыре силы связи «след → инцидент»** (β в logit, заданы до запуска на реальных данных):
  - 0 — контроль: модель обязана не обогнать правило и случайный уровень;
  - 1 — слабая;
  - 2 — средняя, по ней выпускается демо-bundle;
  - 3 — сильная: настоящий пожар или затопление почти всегда даёт срабатывания профильных датчиков.
- Если модель не обходит правило, bundle честно выдаёт откалиброванное правило (`baseline_only`).
- **Частота.** Около 1 инцидента на объект в год на каждый тип.
- **Чем цифры не являются.** Это не качество на реальных инцидентах: они показывают работу конвейера и порядок числа
  нужных меток.
