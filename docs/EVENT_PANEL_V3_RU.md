# Событийная панель v3 (ноутбук 14)

Код: `ml/sensor_failure/event_panel_v3.py` (state machine, цели), `event_panel_v3_kaggle.py` (распаковка, manifest),
`config/state_taxonomy_v3.json` (классы значений). Ноутбук: `notebooks/kaggle/14_event_panel_v3_cpu.ipynb`
(генератор `generate_event_panel_v3_notebook.py`). Тесты: `tests/test_event_panel_v3*.py`.
Правила согласованы в переписке Claude ↔ GPT (Drive, документы 05–12) и подтверждены командой.

## Зачем

Цель v2 `target_failure_state_onset_24h` смешивала «Неисправен» и «Обесточен» в сутках D+2 по дневной панели:
- по FAQ организаторов «Неисправен» означает только потерю связи с устройством, а не поломку;
- дребезг фаз питания давал около 35 % положительных при 1,5 % строк;
- ноутбук 13 фильтровал строки по будущему (старт в D+1), поэтому его результат недействителен.

v3 строит цели по секундному журналу, по одной на пункт ТЗ, и не смешивает их.

## Конвейер

1. **Классификация события.** `значение_датчика` раскладывается по таксономии:
   - технический код (`tech_value`);
   - газ вне диапазона 0–100 %;
   - число;
   - `01.01.1970…` как сбой часов;
   - дата, совпадающая со временем события (дубль timestamp);
   - прочая дата;
   - текстовый класс;
   - `unknown_value`.
2. **Секунда.** Секунда канала — это неупорядоченное множество значений. Порядок строк CSV и `ид_события` не используются.
   - Поток = (канал, класс сигнала), **stream mapping v1** (таксономия 3.1, согласовано с GPT в документе 16). Для каждого потока секунда получает одно из состояний:
     - `F` — есть отказ этого потока, нет его O;
     - `O` — есть однозначное рабочее состояние **того же** потока;
     - `A` — отказ и O вместе (conflict) или неизвестное (U) этого потока;
     - нет сведений — секунда поток не меняет.
   - Связь: F = «Неисправен»; O = только сообщения функции самого канала (норма, событие, число); U = «Неопределен».
     Питание, охрана, затопление и служебные сообщения связь не закрывают.
   - Питание: F = «Обесточен»; O = только явные «Есть питание» / «Питание от сети».
     «Питание от батарей» нейтрально. Во время «Неисправен» без сведений о питании питание неизвестно (U).
   - Классы вне потоков (охрана, затопление, сводки объекта, технические значения) идут в аудит `events_in_no_stream_by_class`.
   - Две заранее объявленные sensitivity-версии:
     - `service_neutral`: «Неопределен» не меняет связь;
     - `power_ok_from_function`: сообщения функции канала = O питания.

     Ноутбук 14 пересобирает разметку в обоих вариантах и выводит только число изменившихся меток. Выбор варианта по validation-метрикам не делается.
3. **RLE и эпизоды.**
   - Эпизод — это блок `F`.
   - Onset `strict`, если предыдущий блок `O`, иначе `ambiguous`.
   - Длительность точная, если следующий блок `O`. Иначе эпизод цензурируется концом данных.
   - `sustained`:
     - 1, если длительность ≥ τ (по умолчанию 5 мин);
     - 0, если точная длительность < τ;
     - null при цензуре.
4. **Грид.** Строка (канал, D) существует, если канал слал события в [D−6; D].
5. **Признаки на конец D.** Используется только прошлое:
   - дневные счётчики классов;
   - окна 7 и 30 суток;
   - статистики чисел;
   - газ;
   - состояние связи и питания на конец D (as-of) и возраст состояния;
   - сутки с последнего onset.
6. **Цели** считаются по окну [D+2; D+3). Решение по метке принимается не позже D+4 (`d_label_decision_end`, L = 24 ч).

## Цели

Каждая цель имеет колонку `reason_*` с одним из значений ниже. `1` = `positive`, `0` = `negative` или `negative_transient_only`. Все остальные причины дают null.

| цель | eligibility на конец D | 1 | null |
|---|---|---|---|
| `target_t2a_link_onset` | связь `O` | strict onset «Неисправен» в D+2 | `no_state_history`, `state_not_ok_at_D`, `window_beyond_data`, `ambiguous_onset`, `unobserved_window` |
| `target_t2b_link_sustained` | связь `O` | strict onset в D+2, эпизод ≥ τ | то же + `censored_duration` |
| `target_t2c_power_onset` / `_sustained` | питание `O` | то же для «Обесточен» | как у T2a/T2b |
| `target_t1a_tech_value` | числа в последние 30 сут и нет технических значений 7 сут | техническое значение или значение вне диапазона в D+2 | `no_measurements_30d`, `recent_tech_value`, `window_beyond_data`, `unobserved_window` |
| `target_t4_gas_cross` | газовый канал, последнее показание < 1 % | строгое пересечение 1 % снизу вверх в D+2 | `not_gas_stream`, `above_threshold_at_D`, `window_beyond_data`, `unknown_previous_reading`, `unobserved_window` |

Дополнительные правила:
- **Onset в D+1** — это competing outcome (`competing_*_d1`), а не фильтр строки. Строка остаётся, и если в D+2 нового onset нет, её метка 0.
- **Тишина.** Если у канала нет событий в D+2 и D+3, строка получает `unobserved_window` → null. Тишина не считается отрицательным примером. У событийных каналов (двери, движение) таких строк много, поэтому coverage показывается отдельно.
- **Эпизод и cooldown.** Эпизод цели (ground truth) не равен 72-часовому cooldown алертов: cooldown — политика выдачи, а не часть метки.
- **Уровень доказательности.** Ни одна цель не является подтверждённым физическим отказом. Это наблюдаемые события журнала, и в бэкенд они уходят как typed scores с `evidence_level`.

## Сверка с независимыми кейсами GPT (Drive, документ 14: C1–C12)

Тесты: `tests/test_event_panel_v3_gpt_cases.py`. Первый прогон сохранён до правок. После него код приведён к правилам, о которых уже договорились:
- **C2/C12.** Если в окне D+2 есть неоднозначная секунда (A-блок), это не отрицательный пример: метка null (`ambiguous_onset`).
- **C7.** `sustained = 1` ставится только при однозначном закрытии эпизода тем же потоком после t0 + τ. Повторы «Неисправен» и тишина непрерывность не доказывают, поэтому незакрытый эпизод даёт `censored_duration`.

После stream mapping v1 (GPT 16) **C3, C8 и C12 закрыты**. C12 теперь даёт T2a = 1: «Есть питание» относится к потоку питания.

Сознательно не закрыт (xfail) только **C5**. Estimand: T2a = «любой strict onset в D+2 у канала, eligible на конец D». Onset в D+1 — флаг `competing_*_d1`: метку он не обнуляет и строку не удаляет. Ноутбук 15 отдельно показывает долю competing и PR-AUC для «первого onset».

Выборка 2019 (каждый 10-й канал), изменения от mapping v1 **[изм]**:
- «Неопределен» есть у **всех** 537 каналов (28 466 событий). Соседние события — почти всегда «Норма»: 88 % перед ним, 95 % после. Это похоже на служебный поток, а не на состояние связи.
- Основная версия (U) против `service_neutral` для T2a: 10 961 метка 0 → null и 5 меток 1 → null.
- Питание по явным значениям: T2c определена у ~0,6 % строк (613 размеченных против 54 917 до mapping). Вариант `power_ok_from_function` возвращает 53 642 меток 0 и 665 меток 1.

## Kaggle-поток (ноутбук 14)

1. **Поиск входов** во всех `/kaggle/input`:
   - `ext-journal-YYYY.{parquet,csv,7z}`; при нескольких форматах одного года приоритет parquet > csv > 7z;
   - `справочник_каналов_датчиков.csv`; имена сравниваются после NFC, потому что macOS даёт NFD.
2. **7z → parquet** по одному архиву за раз. Сохраняются только 6 колонок журнала, все как строки. CSV после конвертации удаляется.
3. **Перераскладка по календарному году события.**
   - Строки, попавшие в файл соседнего года, переносятся в свой год; их число — в `rows_from_other_year_files`.
   - Точные дубли строк удаляются; их число — в `exact_duplicate_rows_dropped`.
4. **Сборка по группам каналов** (`N_BUCKETS`, по хэшу канала). Каналы независимы, поэтому результат не зависит ни от числа групп, ни от разбиения по файлам. Это проверено тестами.
5. **Выход:**
   - `event_panel_v3/event_panel_v3_partNN.parquet`;
   - `panel_manifest_v3.json`: SHA-256 частей, входов и таксономии, конфиг, колонки признаков, целей и причин, колонка purging;
   - `audit_event_panel_v3.json`, `summary_event_panel_v3_ru.md`: только агрегаты.

**Баланс строк** (`stage.row_balance` в manifest и строка в сводке):

источники = в панель + точные дубли + повторённые строки заголовка + строки без года + вне режима; поле `unexplained` должно быть 0.

- В FULL-прогоне 24.09 одна «необъяснённая» строка в 2025 оказалась **повторённой строкой заголовка внутри ext-journal-2025.csv**: проверено подсчётом по сырому файлу, 1 такая строка, 0 строк без даты. Раньше она отбрасывалась без учёта.
- Дубли — только полные совпадения всех 6 колонок, включая `ид_события`.
- Отдельно считается `same_event_id_different_content_kept`: одинаковый `ид_события` при разном содержимом. Такие строки не удаляются.

Ключи каналов и объектов — `sha256("ldt-misis-panel-v3:" + id)[:16]`. Сырых идентификаторов в выходе нет.

**SMOKE**: годы 2019–2020, ≈1/20 каналов, статус `completed_smoke_non_comparable`.

Проверка на реальной выборке (2019, каждый 10-й канал):
- ≈1,5 млн событий, сборка ≈6 с;
- полный журнал 2019–2026 оценочно занимает порядка 10–20 мин CPU на Kaggle.

## Ограничения и открытые вопросы

- Таксономия построена по справочнику и значениям журнала 2019. Для других лет:
  - доля `unknown_value` > 1 % выводится предупреждением в сводке;
  - такие значения нужно разобрать до обучения.
- Технические коды T1a (−127, −100, 255, −3276, −3276.8, 327.68, 3276.7) — фиксированное правило из FAQ и данных 2019, выбранное до любой валидации. Это не универсальные пороги и не доказательство физического отказа датчика.
- Разделение периодических и событийных потоков для coverage (предложение GPT) пока не реализовано. Это отдельные признаки и срез в ноутбуке 15.
- 2021 год — переход системы мониторинга (FAQ). Панель его строит, ноутбук 15 исключает его из обучения и оценки.
