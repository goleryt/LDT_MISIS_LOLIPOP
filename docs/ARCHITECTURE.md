# Архитектура и границы решения

Актуально для октябрьской ветки финальной доработки. База — main `5d64126`.
Доказательства: [FINAL_ACCEPTANCE_2026-10](FINAL_ACCEPTANCE_2026-10.md).

## Процессы

Браузер → nginx → React/TypeScript SPA и FastAPI → PostgreSQL.
Локальный Compose использует PostgreSQL16; существующий Railway — PostgreSQL18.
API: Python 3.14; отдельный ML-runtime: Python 3.12.
Compose: postgres, migrate, backend, frontend, proxy, backup.
Профиль `integrations` запускает GET worker; `ml` — scheduler, ожидающий маркер завершённых суток.
Они не запускаются в базовом профиле. Публичный Railway demo обновлён до RC
19.10.2026; API/DB/миграции и основные flows подтверждены в
[remote acceptance](REMOTE_RC_ACCEPTANCE_2026-10-19.md). Постоянных integration worker,
scheduler и automatic backup service в Railway пока нет.

API не загружает ML-библиотеки. Scheduler читает маркер полноты, вызывает замороженный runtime,
сохраняет неизменяемую ревизию и происхождение результата. Повтор с теми же входами идемпотентен;
изменение входов требует новой ревизии. `POST /predictions/inference` отвечает 503:
расчёта по HTTP-запросу нет. Top-K/cooldown — административная конфигурация, без UI-редактора.

## Данные и транзакции

В public хранятся справочники, события, заявки, пользователи/сеансы, аудит,
интеграционные записи/курсоры, прогнозы, решения, ML-ревизии и heartbeat.
`operational.events`, `archive.events` и `analytics.*` — логические SQL-представления,
без удаления исторических исходных строк. `analytics.repair_history` описывает локальные заявки,
не подтверждённые внешние ремонты.

Сессии и блокировки входа находятся в БД. Карта/тревоги используют процессный кэш
READ_CACHE_SECONDS (0–5 с, по умолчанию 2). Авторизация и аудит выполняются на каждом запросе.
Базовый Compose запускает четыре API-процесса; cloud launcher — два по умолчанию,
с настройкой WEB_CONCURRENCY. Каждый процесс имеет пул 5 + максимум 10 дополнительных соединений.
Общий лимит нужно соотнести с PostgreSQL при развёртывании.

Реестр импорта фиксирует попытку до загрузки. Все строки файла и успешный статус
реестра коммитятся одной транзакцией. Ошибка/прерывание откатывает данные; повтор
возможен после освобождения advisory lock. Ранее успешно загруженный файл распознаётся по хешу с типом импорта.
Курсор integration worker и данные также коммитятся вместе.

## Семантика

- Событие/фактическая тревога — наблюдение датчика. Цвет карты показывает фактическое состояние.
- Прогноз — сохранённый результат конкретной ревизии runtime. Отсутствие результата не означает отсутствие риска.
- Shadow/proxy — оценка наблюдаемого пересечения газом 1 % CH4, не вероятность пожара, подтопления, НСД или отказа.
- Рекомендация — предложение runtime с происхождением, требует оценки человека.
- Черновик — редактируемая заявка по рекомендации, ещё не подтверждённая диспетчером.
- Заявка — локальный рабочий документ со статусом и историей изменений.

Связь prediction/recommendation → request сохраняется идемпотентно под блокировкой строки.
История заявки содержит actor, role, время, переход статуса и имена изменённых полей.
Admin/dispatcher проверяет draft; technician не может подтвердить его.

Текущий UI передаёт `expected_updated_at` при изменении заявки. После блокировки строки
сервер сравнивает версию: устаревшая правка возвращает 409 без изменения данных/истории.
Одновременные правки проверены двумя потоками: один успех, один конфликт.
Для совместимости старые REST-клиенты могут опускать версию; у них остаётся
блокировка строки, но защиты от последовательной устаревшей правки нет.

## Интерфейс и эксплуатация

Маршруты: `/`, `/objects`, `/alarms`, `/events`, `/imports`, `/requests`,
`/predictions`, `/reports`, `/settings`. Login — общий SessionGate.
Точки без реальных координат явно условные; реальные Point GeoJSON/WKT поддерживаются.
HTTP-клиент ограничивает ожидание, показывает безопасную ошибку;
граница React ошибок позволяет восстановиться обновлением страницы.
Уведомления опрашиваются последовательно после предыдущего запроса,
ссылка ведёт к точному объекту/каналу; прочтение индивидуально для пользователя.

`/health` проверяет процесс; `/ready` — подключение и текущую Alembic head.
Admin `/api/v1/operations/status` показывает last_seen/last_success worker,
последний импорт, ML-job, ошибки источников, backup marker и пул текущего процесса.
Heartbeat — последнее наблюдение, не самостоятельный внешний мониторинг живого процесса.
Пул не агрегируется по всем API-процессам.

Operations также возвращает version/commit; `unknown` допустим, если идентификатор
сборки не передан. Невалидный JSON или timestamp backup marker отображается как
ошибка metadata, не приводит к отказу всего endpoint. Первая автоматическая копия
зависит от успешного завершения миграций.

Отдельный `infra/Dockerfile.cloud` собирает frontend и API/nginx в одном web-образе.
API слушает только loopback; TLS завершает внешняя платформа. Tini обрабатывает
ранние сигналы PID1, launcher завершает дочерние процессы и выходит при их отказе.
Старт не создаёт пользователей, не загружает данные, не запускает inference и миграции.
Последние выполняются отдельной задачей. Scheduler/worker/backup — отдельные процессы.
Проверка этой упаковки и последовательность публикации: [DEPLOYMENT_RC](DEPLOYMENT_RC.md).

Отчёты: фактические наблюдения и локальные заявки, JSON/XLSX/PDF, период до 367 дней,
до 5000 строк с явным усечением, источник/период/время формирования/количество строк.
XLSX нейтрализует формулы; PDF использует Noto Sans с лицензией.

Для эксплуатации нужны реальные подключения, AD/сертификаты, защищённый внешний аудит,
копии вне узла, мониторинг и проверка восстановления на полном архиве.
