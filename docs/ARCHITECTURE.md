# Архитектура и границы решения

Основа доработки: актуальная ветка локального репозитория, коммит b276e52. Загруженный старый архив не использован как база изменений. Оригинальная рабочая папка и БД не изменялись.

## Компоненты

Браузер → nginx (HTTPS) → React SPA / FastAPI → PostgreSQL.
Отдельные процессы: Alembic миграции, worker интеграций, ежедневное резервное копирование.
Фронтенд сохраняет карту, объекты, выбор датчика, историю, тревоги, журнал событий и заявки.
Новые элементы: вход/выход, уведомления, журнал прогнозов и решений.

Данные мониторинга и результаты модели — разные сущности. Срабатывание датчика не превращается в вероятность риска.
Все исходящие обращения worker к системам заказчика используют GET; управление оборудованием и отправка заявок во внешние системы отсутствуют.

## Хранение

public: исходные справочники, события, заявки, пользователи, сессии, аудит, записи интеграций, прогнозы и решения.
operational.events: последние 90 дней и записи с неизвестным временем.
archive.events: более ранние наблюдения.
analytics.daily_observations, analytics.repair_history: представления фактической статистики.

Это логическое разделение в одной PostgreSQL, без удаления или физического перемещения исторических событий; сохраняются существующие запросы истории. Физическое архивное хранилище, сроки хранения и индексы под полный 12-летний массив согласуются с заказчиком. Нулевое число прогнозов не означает нулевой риск.

Карта и текущие тревоги используют процессный кэш на 2 секунды (READ_CACHE_SECONDS, диапазон 0–5); авторизация и аудит выполняются для каждого обращения независимо от кэша. Контейнер запускает 4 процесса API (WEB_CONCURRENCY), по 5 постоянных и до 10 дополнительных соединений БД на процесс. Размер пула и число процессов согласуются с лимитом PostgreSQL.

Раздел «Отчёты» экспортирует фактические наблюдения и историю заявок в XLSX/PDF. Период ограничен годом, результат — 5000 строками с явной отметкой усечения. Формулы из пользовательского текста в XLSX обезвреживаются, PDF использует открытый Noto Sans с приложенной лицензией.

## Обработка данных

CSV UTF-8/UTF-8 BOM; XLSX — первый лист с заголовком, формулы запрещены; JSON — массив записей; XML — records/record с плоскими полями, DTD и сущности запрещены. Ограничения: 50 MiB исходного файла, 200 MiB распакованного XLSX, 250000 строк, 2000 записей за API-пакет. Заголовки канонических файлов сохранены на русском.
Пустые значения нормализуются; числовые значения с запятой поддерживаются; NaN/Infinity не попадают в числовые графики.
Исторические дата/время интерпретируются в SOURCE_TIMEZONE (по умолчанию Europe/Moscow). API потока требует явного часового пояса.
Все партии одного файла фиксируются атомарно. Хеши строк сохраняют совместимость с исходным импортом. Хеш реестра учитывает тип импорта; повтор старого файла безопасен за счёт хешей строк.
Сессионная advisory-блокировка PostgreSQL предотвращает одновременную обработку одного файла. После аварийного завершения процесс можно повторить.

## ML-граница

app.predictions.PredictionProvider — интерфейс predict(object_id).
PredictionResult требует внешний ID, объект/датчик, тип инцидента, вероятность [0,1], горизонт ≥24 ч, расчёт/целевое время с часовым поясом, версию модели; рекомендация необязательна.
Сейчас фабрика возвращает UnconfiguredProvider. /predictions/status сообщает model_not_configured; /inference возвращает 503, не записывая прогноз и уведомление.
Ни seed, ни mock-source, ни тесты не генерируют ML-результаты.
При подключении реальной модели необходимо реализовать фабрику и отображение готовности, задать таймаут/очередь inference и подтвердить норматив ≤300 секунд. Решения, исходы, версии и связь с заявками уже имеют схему хранения и UI.
Вероятность и рекомендация могут поступить только из настоящего провайдера; «ручного добавления прогноза» через API нет.

## Надёжность и ограничения

Сессии и блокировки попыток входа хранятся в БД, поэтому не теряются при смене worker.
Аудит фиксирует начало запроса до бизнес-операции и итог после неё. Если процесс погиб между ними, запись остаётся с outcome=null и требует сопоставления с состоянием сущности. Если итоговая запись аудита недоступна, клиент получает 503; перед повторением изменяющей операции нужно обновить состояние.
HTTP-проверка /health проверяет процесс, /ready — доступность схемы БД.
Для полноценной эксплуатации нужны внешний мониторинг, экспорт аудита в защищённое хранилище, секреты и резервные копии вне узла, согласованные RPO/RTO.
