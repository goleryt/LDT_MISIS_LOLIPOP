# Импорт CSV/XLSX: конкурентная нагрузка и атомарность

Дата: 20.10.2026, Europe/Moscow. Ветка `release/final-rc`.
Нагрузочный gate перед следующим обновлением публичного Railway.
До получения этого требования Railway уже был обновлён до `ae43e33`;
все описанные ниже стрессовые и аварийные проверки выполнены **только локально**.

## Среда и методика

- Новые контейнеры `ldt-import-load-web` и `ldt-import-load-db`, отдельные сеть
  `ldt-import-load` и БД `ldt_import_load_qa`. HTTP только `127.0.0.1:18094`.
- Web: production Dockerfile.cloud, nginx, два Uvicorn workers, лимит 1 GiB / 2 vCPU.
  PostgreSQL 18: отдельный контейнер, 1 GiB / 2 vCPU, max_connections=100,
  shared_buffers=128 MB, work_mem=4 MB. Это не аппаратная конфигурация Railway.
- Начальные синтетические данные: 20 000 событий, 50 объектов, 1000 каналов.
  Каждый файл содержит 10 000 событий: CSV 460 123 bytes, размер XLSX см. JSON.
  В сценарии 20 разных файлов проверялось 200 000 новых строк + начальные 20 000.
- Синхронный старт 5/10/20 клиентов; CSV и XLSX отдельно, одинаковые/разные файлы,
  затем смешанные CSV/XLSX. Уникальные файлы после 409/429 повторяются парами.
  Отказы admission не считаются успешными импортами или скрытой очередью.
- Параллельно постоянно вызываются `/health`, `/api/v1/map/objects`,
  `/api/v1/imports`, с timeout 5 s. Кэш чтения отключён.
- RAM/CPU: cgroup counters; соединения, активные транзакции и занятые слоты:
  pg_stat_activity/pg_locks. Перезапуск собственного web перед каждым сценарием
  сбрасывает его memory.peak. PostgreSQL между сценариями не перезапускается.
  PG target sessions включают одно соединение измерителя; общий total также
  включает фоновые PostgreSQL процессы. Это не число одновременно работающих SQL.
- Baseline: замороженный image `ldt-railway-release:edb9a15`; исходники механизма
  импорта совпадали с `ae43e33`. Исправленный image: `ldt-import-load:fixed`.
  Последняя mixed-v2 серия выполнена на финальных исходниках этого изменения.

## Обнаруженные причины

1. Каждый импорт держал соединение advisory lock и требовал дополнительные
   соединения для данных/реестра/audit. При 10/20 загрузках пул 5+10 на worker
   исчерпывался. Зафиксированы QueuePool timeout 30 s, 503 и таймауты обычных API.
   В CSV/20 фактически сохранились 160 000 строк, хотя ответы 200 сообщали только
   о 130 000: ошибка после commit могла скрыть успешную запись от клиента.
   Атомарность файла и однозначность HTTP-результата — разные свойства.
2. Одновременный повтор уже обрабатываемого файла возвращал вводящий в заблуждение
   400. Данные не дублировались, но клиент не получал правильного retry-сигнала.
3. Каталог объектов целиком накапливался в памяти и записывался одним INSERT:
   большой файл превышал бы лимит 65 535 параметров PostgreSQL.
4. Одинаковые ID в одном batch upsert каталога вызывали cardinality error;
   счётчики каталогов не отражали повторы. Это отдельный дефект, покрыт тестами.

## Изменения

- Два глобальных неблокирующих PostgreSQL advisory slots на всю БД, включая
  разные web workers/реплики. Одно соединение держит и slot, и прежний file lock.
  SELECT-транзакция блокировки сразу завершается; session locks остаются до finally
  либо потери соединения. Все реплики должны иметь одинаковый IMPORT_MAX_CONCURRENT.
- nginx принимает не более четырёх одновременных upload-запросов на instance;
  backend обрабатывает не более двух файлов на общую БД. Пул чтения не расширялся.
- Занято: HTTP 429 / IMPORT_CAPACITY_BUSY либо IMPORT_UPLOAD_CAPACITY_BUSY;
  тот же активный файл: HTTP 409 / IMPORT_ALREADY_PROCESSING; Retry-After: 3.
  При конкурирующих ограничениях 429 допустим и для одинакового файла.
  Нет durable queue: отклонённый файл не поставлен в обработку.
- UI сообщает причину, оставляет выбранный файл и позволяет повторить загрузку.
- Общий бюджет обработки 240 s, SQL timeout не больше 60 s и остатка бюджета;
  превышение/отмена SQL → 408, транзакция файла откатывается, реестр failed.
  Таймаут proxy 310 s. Это локальная защита, не обещание обработки файла за 240 s.
- XLSX: read_only, суммарно не более 64 MiB после распаковки, максимум 4096 ZIP
  members / 4 MiB central directory. EOCD проверяется до выделения ZipInfo.
  Прежние лимиты upload/строк и проверки формата сохранены.
- Объекты записываются пакетами по 1000 в **одной** транзакции файла.
  Для повторяющихся ID каталогов сохраняется прежняя последовательная семантика
  «последняя строка побеждает»; статистика разделяет строки/уникальные ID/повторы.
- Deadlock/serialization failure: полный rollback и одна ограниченная повторная
  попытка в том же бюджете; повторная неудача → 429. ML и scheduler не изменялись.

## Аварии, дубликаты и регрессии

[Фактический fault report](evidence/import-load-2026-10-20/faults.json):

- CSV/XLSX: неверная последняя строка после 5000 строк → 400, failed, 0 событий.
- Два разных хеша с 8000 одинаковыми событиями в обратном порядке и повтором строки
  → ровно 8000 событий; повтор завершённого файла idempotent. Число реально
  обнаруженных deadlock записано в JSON; искусственный deadlock также покрыт pytest.
- Отмена реально заблокированного INSERT → 408, failed, 0 событий; retry → 10 000.
- SIGKILL собственного web после наблюдённого uncommitted INSERT → 0 событий,
  session locks освобождены; после restart/reupload → completed, 20 000.
- Обрыв multipart до передачи backend → 0 записей реестра/событий; ready=200.
- Сжатый XLSX с >64 MiB распакованного содержимого → 400 до декодирования.

При гибели процесса реестр может остаться `processing` до повторной загрузки.
Это **не** durable queue/автоматический recovery daemon. Пользователь проверяет
реестр и повторяет тот же файл: file hash и атомарность защищают от дублей.
Преднамеренный SIGKILL/cancel не включаются в статистику обычной доступности.

Дополнительные pytest: 429/409/408, audit отказа, retry, освобождение locks при
Exception/KeyboardInterrupt, exhausted deadlock retry, ZIP directory bound,
duplicate ID каталогов CSV/XLSX, 15 000 объектов в пакетах по 1000, поздняя ошибка
после 3000 объектов → полный rollback. Focused: 23 PASS.
Полный backend: **151 PASS**, 4 dependency warnings, 195.83 s.
TypeScript/Vite PASS; lint 0 errors / 10 прежних warnings.
Chrome: **30 PASS / 8 explicit skips** на изолированной QA. Skips требуют сохранённого
ML-результата/обычного draft fixture, mock environment либо opt-in visual run;
ради этой проверки новые модельные результаты не создавались.

## Воспроизведение без доступа к Railway

1. Создать **новые** local Docker network/PG18/web с точными именами выше, только
   loopback port 18094, указанными лимитами, БД `ldt_import_load_qa`.
   Случайные локальные credentials хранить в env-файле вне Git; ENVIRONMENT=test,
   SECURE_COOKIES=false только здесь, READ_CACHE_SECONDS=0, IMPORT_MAX_CONCURRENT=2,
   CORS_ORIGINS=http://127.0.0.1:18094,http://localhost:18094. Без разрешённого
   browser Origin login корректно вернёт 403; первоначальный browser запуск
   остановлен по этой ошибке конфигурации QA, затем повторён с правильным Origin.
2. Собрать `docker build -f infra/Dockerfile.cloud -t ldt-import-load:fixed .`.
   В web выполнить `alembic upgrade head`, затем `python -m scripts.seed_test_data`
   с TEST_USERNAME/TEST_PASSWORD и SEED_EVENT_COUNT=20000. Web startup сам не seed.
3. В окружении оператора задать RUN_IMPORT_LOAD=true, TEST_USERNAME/TEST_PASSWORD,
   IMPORT_LOAD_DOCKER (при необходимости), приватный каталог generated files.
4. `python tests/import_load.py --require-pass --output <local evidence>/limited --work-dir <private files>`
   и `python tests/import_load.py --require-pass --formats mixed --modes different --output <local evidence>/mixed-v2 --work-dir <private files>`.
5. После завершения load задать IMPORT_LOAD_WORK_DIR/IMPORT_LOAD_OUTPUT и выполнить
   `python tests/import_faults.py`. Он намеренно останавливает **свой QA web**.
   Никогда не направлять эти проверки через Railway URL/DB/tunnel.
6. pytest только ENVIRONMENT=test / POSTGRES_DB=ldt_test в другой выделенной БД;
   `npm run build`, `npm run lint`, Chrome Playwright на локальном QA.

Скрипты требуют opt-in, фиксированные localhost port/container binding/current_database;
удаляют только generated records и реестр в этой новой QA-БД. Рабочие volumes
не удаляются. Перенос этих команд на demo/production запрещён.

## Ограничения и решение gate

- Это приёмка 10k строк/файл при 5/10/20 предложенных загрузках. Не доказана
  производительность всех файлов максимального размера, полного промышленного
  архива или произвольного workbook. Нет нового нормативного SLA от заказчика.
- API ожидает конечный результат; клиент после 409/429 повторяет вручную с учётом
  Retry-After. Автозапуска и background queue не добавлено.
- Импорт XLSX всё ещё требует памяти декодера; ограниченные slots/ZIP limits
  снижают риск, но не заменяют мониторинг реального deployment.
- Статус публичного deployment и последующего обычного smoke — отдельный
  [Railway acceptance](RAILWAY_RELEASE_ACCEPTANCE_2026-10.md).
- **Gate PASS** в указанном объёме: полная матрица, финальная mixed серия,
  аварии, 151 backend test, frontend build/lint, Chrome regression.
  В limited + mixed-v2: **2871 обычный API-запрос / 0 ошибок**, 0 OOM,
  точное число уникальных строк после retry. Нормальный CI и safety backup
  остаются обязательны перед публичным rollout.
  Итоговое решение, команды и локальные hashes исходников:
  [gate.json](evidence/import-load-2026-10-20/gate.json).
