# ML для backend: пакет v1 (ЛЦТ 2026, ДЖКХ)

Этот файл объясняет, что лежит в пакете, как это вызывать, что показывать в интерфейсе и как потом без переделок
заменить модель.

## 1. Что в пакете

```
LCT_ML_backend_v1/
├── README_BACKEND_RU.md          ← этот файл
├── lct_ml_runtime.py             ← единая точка входа: backend вызывает только его
├── requirements.txt              ← точные версии (numpy 2.0.2, pandas 2.3.3, lightgbm 4.6.0, polars 1.35.2)
├── bundles/
│   ├── ACTIVE.json               ← какой газовый bundle активный
│   ├── gas_cross_v3_bundle.zip (+ .sha256)     ← газовая модель G2 (реальная модель)
│   └── incident_head_bundle.zip (+ .sha256)    ← модуль реестра инцидентов (сейчас на заглушке)
├── demo/
│   ├── incident_register_stub.csv              ← заглушка реестра инцидентов (для демо)
│   └── incident_register_coverage_stub.json    ← её покрытие
├── examples/
│   ├── example_run.py            ← пример ежедневного вызова
│   └── example_output.json       ← пример ответа (на синтетическом журнале)
└── docs/                         ← подробные контракты и результаты проверок
```

Контрольные суммы:
- `gas_cross_v3_bundle.zip` — `1747b09c0a289f8509b1ef066442936f315c4f7958d1815825a7f90296503e20`;
- `incident_head_bundle.zip` — `3c8b4b46ae8b17f12a5e6aa16e3722a9907817c65c73cbed3a06880203d1e2c5`.

Runtime сам сверяет SHA-256 каждого ZIP с файлом `.sha256` и отказывается загружать подменённый или неподписанный bundle.

## 2. Быстрый старт

```bash
pip install -r requirements.txt        # Python 3.11–3.12, CPU, интернет не нужен
```

```python
from lct_ml_runtime import MLRuntime

runtime = MLRuntime("bundles/")                 # один раз при старте процесса (SHA, распаковка, загрузка)
out = runtime.score_day(
    journal_files=["journal_2025.csv", "journal_2026.csv"],
    catalogue_file="catalogue.csv",
    as_of_date="2026-06-20",                    # D — признаки строго на конец этих суток
    request_id="daily-2026-06-20")
```

Вызывать **раз в сутки** после закрытия суток D, по всем объектам сразу. Модель не надо загружать заново на
каждый запрос.

### Вход

- **Журнал:** CSV или parquet с колонками исходной выгрузки: `ид_события`, `ид_канала_данных`, `дата`, `время`,
  `тревожное`, `значение_датчика`. Названия колонок — ровно как в данных организаторов.
- **История:** не меньше **400 суток до D**. Иначе газовый bundle отказывает с `INSUFFICIENT_HISTORY`, это защита от
  расхождения с обучением.
- **Будущее:** события позже D runtime отбрасывает сам.
- **Справочник каналов:** `ид_канала_данных`, `ид_объект`, `тип_датчика`, `тип_инж_системы`.
- **Опционально:**
  - `recent_incidents` — подтверждённые инциденты, начатые за последние 7 суток: по ним модуль инцидентов не выдаёт
    прогноз, потому что инцидент уже идёт;
  - `ppr_windows` — окна ППР с подтверждённым соответствием объектов: дают `verified_schedule`.

Время: на реальном журнале это сборка панели по всей истории. Минуты, не секунды: запускайте фоновой задачей.
Предупреждения polars `Sortedness of columns cannot be checked` безвредны.

## 3. Что возвращает `score_day`

```json
{"runtime_version": "...", "as_of_date": "D", "request_id": "...",
 "bundles": [...версии, SHA, статусы...], "primary_gas": "gas_cross_v3_bundle",
 "gas": [ ...по одной записи на канал... ],
 "incidents": [ ...по одной записи на объект × тип инцидента... ],
 "maintenance_context": [ ...только объекты с отметкой... ]}
```

Полный пример формы — `examples/example_output.json`.

### 3.1. `gas` — газовая модель G2

Что предсказывает: **будет ли у газового канала пересечение 1 % CH4 снизу вверх в сутки D+2**. Признаки берутся на
конец D. Это наблюдаемое в журнале событие, **не вероятность пожара и не подтверждённый инцидент**.

| поле | что показывать |
|---|---|
| `score` | Калиброванная оценка 0–1 или `null`. Используется для ранжирования каналов. |
| `decision_status` | `experimental_shadow` — прогноз есть; `abstain` — прогноза нет, причина в `reason_codes`. |
| `reason_codes` | Для abstain: `NOT_GAS_STREAM` (не газовый канал), `NO_GAS_READING_AT_D` (нет показаний на D), `ABOVE_THRESHOLD_AT_D` (газ уже ≥ 1 %: это текущая тревога, а не прогноз). |
| `window_start`, `window_end_exclusive` | Окно прогноза [D+2; D+3). Брать из ответа, не вычислять самим. |
| `ид_канала_данных`, `ид_объект` | Где. Физических координат нет. |
| `maintenance_context` и др. | См. п. 3.3. |
| `target_code`, `model_version`, `evidence_level`, `score_kind`, `operational_ready` | Хранить вместе с прогнозом, для аудита и смены модели. |

Правила показа:
- Показывать **top-25 каналов в сутки** с cooldown 72 ч: один канал не чаще раза в 3 суток. Это делает backend.
- Автоматических заявок и критических уведомлений по этому score **нет**, режим — shadow.

### 3.2. `incidents` — модуль реестра инцидентов (демо)

По каждому объекту и типу (`пожар`, `подтопление`, `нсд`) — оценка начала инцидента в сутки D+2.

**Сейчас модуль обучен на заглушке реестра:** `label_source = "stub"`, `evidence_level = "E4"`. Реальных
подтверждённых инцидентов в данных нет. В интерфейсе рядом обязательно показывать плашку:

> ДЕМО: модель обучена на заглушке реестра. Оценка показывает работу конвейера, а не вероятность реального инцидента.

Текст плашки также приходит в поле `score_meaning`.

| поле | что это |
|---|---|
| `decision_status` | Для типа инцидента: `baseline_only` — score = откалиброванное правило «тревоги профильных датчиков за 7 суток» (модель не доказала преимущество); `insufficient_labels` — мало меток, прогноза нет; `demo_stub` / `experimental_shadow` — выдаёт модель. |
| `abstain_reason` | `INSUFFICIENT_LABELS`, `ONGOING_INCIDENT`, `OBJECT_NOT_COVERED` |
| `top_factors` | До трёх факторов риска словами («пожарные датчики: тревоги за 7 сут»). Для карточки прогноза. |

Сейчас:
- пожар и подтопление — `baseline_only`;
- НСД — `insufficient_labels`, то есть abstain. Это честный результат проверки, а не ошибка.

Когда заказчик даст реальный реестр, модуль переобучается одной командой (см. `docs/INCIDENT_REGISTER_CONTRACT_RU.md`,
п. 5). Приходит новый ZIP, код backend не меняется.

### 3.3. `maintenance_context` — «вероятно, после ТО/поверки»

Проверка на исторических данных (`docs/results_17_maintenance_audit_summary_ru.md`) показала, что большинство
пересечений газа 1 % — следы поверки газоанализаторов. Датчики объекта несколько суток молчат (их снимают), потом
возвращаются и показывают контрольную газовую смесь (около 2,2 %).

| период | помечено строк | в них пересечений 1 % |
|---|---|---|
| 2025 H2 | 13 % | 94 % |
| 2026 H1 | 6 % | 66 % |

Значения поля:
- `possible_recent_silence` — все газовые каналы объекта молчали ≥ 4 суток подряд, молчание закончилось за последние
  21 сутки, показания вернулись. Считается только по прошлому. Дополнительно приходят `silence_length_days` и
  `silence_ended_days_ago`.
- `verified_schedule` — объект в переданном окне ППР (`ppr_windows`). Включать, только когда сверено соответствие
  «Объект N» из графика ППР и `ид_объект`.
- `unknown` — отметки нет.

Правила:
- **Score и тревогу не скрывать.** Показывать пометку «вероятно, после ТО/поверки» и отдавать на ручную интерпретацию
  диспетчеру.
- Подавлять ли такие тревоги, решает заказчик, не модель.

## 4. Насколько модели можно верить (коротко и честно)

- **G2, проверка по времени на 2025 H2** (модель этот период не видела):
  - PR-AUC 0,352 против 0,059 у простого правила при доле событий 0,017;
  - калибровка ECE ≈ 0,006;
  - на 2026 H1 — 0,143 против 0,037.
- **Ограничение 1.** Большая часть этого качества — предсказание поверок, см. п. 3.3. Вне окон поверок модель тоже
  лучше правила (lift 20–34× против 3–5×), но событий там 33–117, и статистическая граница почти ноль.
- **Ограничение 2.** У половины тревог top-25 исход потом не наблюдался.
- **Итог.** Отсюда режим shadow, запрет автозаявок и формулировка «прогноз наблюдаемого пересечения», а не «прогноз
  пожара».
- **Модуль инцидентов** — демонстрация архитектуры на заглушке. Его цифры не являются качеством на реальных инцидентах.

## 5. Правила интеграции — чтобы новая модель встала без переделок

Мы продолжаем эксперимент: газовая модель, обученная только на пересечениях **вне** поверок. Если она пройдёт
заранее заданный порог, придёт новый ZIP. Чтобы замена заняла минуты, backend соблюдает пять правил:

1. **Вызывать только `lct_ml_runtime.MLRuntime`.** Не собирать признаки своим кодом и не импортировать `predictor.py`
   напрямую: признаки считает код внутри bundle.
2. **Ничего не хардкодить:** названия и число признаков, `target_code`, окно, тексты, пороги — всё из ответа.
   Хранить `model_version` и `bundle` вместе с каждым прогнозом.
3. **Модели — это файлы в папке `bundles/`.** Путь к папке задаётся в конфиге.
4. **`maintenance_context` показывать при любой модели.** Он считается runtime'ом из журнала, от модели не зависит.
5. **Зависимости — строго из `requirements.txt`.** Новые bundle собираются на тех же версиях.

Как заменить газовую модель:
1. Положить `gas_cross_v4_bundle.zip` и `gas_cross_v4_bundle.zip.sha256` в `bundles/`.
2. На время сравнения оставить активной v3 и вызывать `score_day(..., all_gas_bundles=True)`. Придут прогнозы обеих
   моделей с полями `bundle` и `is_primary`, в UI показывать только `is_primary = true`.
3. Переключить: `ACTIVE.json` → `{"gas": "gas_cross_v4_bundle"}` и перезапустить процесс.
4. Откат: вернуть `ACTIVE.json` на v3. Файлы v3 не удалять.

Модуль инцидентов заменяется так же: новый ZIP с тем же именем плюс `.sha256`.

Если эксперимент не пройдёт порог, ничего не меняется: остаётся v3.

## 6. Ошибки

| исключение | когда | что делать |
|---|---|---|
| `RuntimeContractError` при старте | нет `.sha256`, SHA не совпадает, ACTIVE.json указывает на отсутствующий bundle | не запускать ML, сообщить ML-команде |
| `ContractError: INSUFFICIENT_HISTORY` | в журнале меньше 400 суток до D | передать больше истории |
| `RuntimeContractError` в `score_day` | нет или неверна `as_of_date` (нужно `YYYY-MM-DD`) | исправить вызов |

## 7. Чего не делать

- Не создавать заявки и критические уведомления автоматически по любому score.
- Не складывать и не усреднять score газа и разных типов инцидентов.
- Не называть газовый score «вероятностью пожара», а score модуля инцидентов при `label_source = stub` — вероятностью
  инцидента.
- Не логировать сырые записи журнала в ML-логах. Не менять файлы внутри bundle: сломается SHA.
