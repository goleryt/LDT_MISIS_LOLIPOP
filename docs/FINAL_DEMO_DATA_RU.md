реальными объектами заказчика. Координаты на схеме вычисляются из ID и не
устанавливают физическую географию. Оценки не объединяются в вероятность аварии.

## Подготовка и повторение

Инструмент `backend/scripts/prepare_final_demo.py` по умолчанию только читает
БД. Требует точное имя целевой базы и `ENVIRONMENT=test`; в production дополнительно
проверяет известные Railway project/environment. Не запускается при startup.
Пароли и DB URL передаются через существующее приватное окружение, не аргументы.

Из backend, в уже настроенном отдельном тестовом окружении:

```sh
python -m scripts.prepare_final_demo --expected-database ldt_final_models_seed
python -m scripts.prepare_final_demo --expected-database ldt_final_models_seed --export-gas-inputs /work/final-demo-inputs
```

Первый вызов выдаёт inventory: namespace/version, подтверждённые ID, привязки,
версии, входные и выходные fingerprints, оценки, даты, checksum исходной истории.
Второй воспроизводит исходный газовый генератор 29 сентября без изменения формул
входного примера. Неизвестные существующие файлы и коллизии зарезервированных ID
блокируют запись. Сам экспорт не запускает inference и не пишет в БД.

Для НОВОЙ изолированной QA-базы: сначала Alembic upgrade head, затем отдельно
в газовом Python 3.12 runtime с неизменным bundle:

```sh
# Отдельный явный opt-in в окружении: PUBLISH_FINAL_GAS_DEMO=synthetic-input-only
python -m scripts.prepare_final_demo --expected-database ldt_final_models_seed --publish-gas
```

Создаются только зарезервированный синтетический объект, три канала и исходные
3870 наблюдений. Существующий атомарный importer и frozen `run_daily` выполняют
расчёт. Рекомендации/пороги/очередь не меняются. Полный ранее рассчитанный gas
на эту дату переиспользуется, автоматических заявок/уведомлений нет.

SF/Fire требуют отдельный scenario runtime, прежние SCENARIO_* flags и операторские
opt-ins, описанные в `publish_synthetic_scenario_demo.py`. Пример фактически
проверенного нового QA-снимка:

```sh
python -m scripts.prepare_final_demo --expected-database ldt_final_models_seed --publish-scenarios --as-of-date 2026-10-19
```

Дата фиксируется в manifest. Повтор того же источника/даты/версий возвращает
`reused=true`. Для уже сохранённого публичного снимка дата — 18.10.2026.
Если исторический снимок ещё не существует, поздний новый расчёт может корректно
дать LATE_RUN/недоступность: нельзя подделывать время выпуска ради доступности.
Для воспроизведения старого сохранённого состояния служит проверенный backup.

## Свежие доказательства

`docs/evidence/final-product-2026-10/`: gas replay без сети, SF/Fire runtime smoke,
новый dataset manifest и подтверждение идемпотентности. В новой QA-БД получены
3 gas + 2 SF + 1 Fire; при повторении число строк не растёт. Отсутствие истории
проверено реальным runtime как unavailable; такой результат не показан как 0.

Карта читает `/api/v1/map/forecasts`; этот GET не запускает inference. Gas виден
вне Top-K, включая abstain, с сохранением рабочей очереди. SF/Fire читаются из
последнего снимка; failed/partial не подменяется предыдущим успешным расчётом.
Неподтверждённые привязки не получают случайную точку. Для ограниченного ответа
API явно сообщает truncation после 500 строк каждого контура.

## Сохранность и проверочные данные

Перед изменениями public получен новый backup с checksum и восстановлением
173868 событий в НОВУЮ БД; существующая Railway-БД не восстанавливалась поверх.
Оригинальный журнал и аудит сохранены. История ручных проверок/заявок полезна
для воспроизводимости; неизвестные по происхождению записи не удаляются.
Массовой очистки и SQL DELETE рабочих данных нет. Тестовые новые seed/inference
этого этапа выполнены в отдельных локальных БД, не на Railway.

Публичные demo-реквизиты в исходном PPTX обнаружены: пароль роли manager заменён,
старые сессии инвалидированы, права остались read-only, действие записано в аудит.
Новый пароль хранится вне Git и отдельно от PPTX/PDF/архива поставки.
