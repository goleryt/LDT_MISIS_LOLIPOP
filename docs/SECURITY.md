# Доступ и безопасность — актуализация 16.10.2026

Без входа доступны только health/ready и CORS preflight. Остальные API, OpenAPI и документация требуют сеанса.
Локальные пароли: PBKDF2-SHA256, случайная соль, 600000 итераций; минимум 12 символов. Нет встроенной учётной записи и пароля.
Случайные сессионные токены хранятся в БД только в виде SHA-256; cookie HttpOnly/SameSite=Strict, Secure обязательно в production.
Изменяющие запросы с cookie требуют X-CSRF-Token. Токен CSRF возвращается только авторизованному клиенту.
Лимит входа: 10 попыток на имя за 15 минут, плюс ограничение nginx по IP. Активность и роль пользователя проверяются на каждом запросе.
Создание, отключение и выпуск машинного токена — python -m app.admin; операции тоже записываются в аудит.
Машинные токены действуют 24 часа и применимы только к роли integrator; плановая ротация — задача администратора.

## LDAP/AD

AUTH_PROVIDER=ldap. Настроить LDAP_HOST (имя сервера, не URL), LDAP_PORT=636, LDAP_BASE_DN, LDAP_BIND_DN, LDAP_BIND_PASSWORD, LDAP_CA_FILE и LDAP_ROLE_GROUPS (JSON: полный DN группы → роль).
Используется LDAPS с обязательной проверкой сертификата, read-only соединениями и отключёнными referrals. Поиск по экранированному sAMAccountName или uid, затем bind от имени найденного пользователя.
Группа должна быть явно сопоставлена. Вложенные группы AD рекурсивно не раскрываются: назначьте непосредственную группу приложения либо предоставьте согласованный механизм развёртывания групп. При недоступности каталога нет автоматического перехода на локальный пароль.
Сеансы имеют ограниченное время жизни; отключение в AD учитывается при новом входе, экстренное отключение активного сеанса выполняется локальной командой disable-user. Для немедленной централизованной ревокации требуется согласовать события каталога/SSO с заказчиком.

## Аудит

Записываются actor, role, timestamp, action (HTTP-метод), target (путь), request_id, entity_type/entity_id и outcome (HTTP-результат), включая отказ в доступе. Для анонимного отказа и исторических записей применимые поля могут быть null; это не подменяется фиктивным пользователем.
Тела запросов, пароли, cookie и заголовки авторизации не записываются.
История решений хранит автора, действие, основание, комментарий и фактический исход.
БД приложения не заменяет независимое неизменяемое хранилище аудита; защита от администратора БД требует SIEM/внешнего архива заказчика.

## Развёртывание

TLS 1.2/1.3 на nginx, сертификат и ключ монтируются read-only, backend и БД не имеют опубликованных портов.
В production задаются явные ALLOWED_HOSTS, HTTPS CORS_ORIGINS, SECURE_COOKIES=true; mock запрещён конфигурацией.
Внешние интеграции используют отдельные read-only учётные данные; источники настраивает администратор, URL не принимаются от пользователя API.
Данные обезличивает источник согласно ТЗ. Сервис не заявляет юридическую сертификацию или автоматическое обезличивание произвольного текста.

Основание TLS-настроек LDAP: [ldap3 SSL/TLS](https://ldap3.readthedocs.io/en/latest/ssltls.html).

## Свежая автоматическая проверка

`tests/test_security_acceptance.py` проверяет серверную матрицу admin/dispatcher/technician/analyst/manager,
401/403, CSRF, истечение/выход и атрибуцию аудита. `test_request_drafts.py` проверяет
ограничение draft, историю и переходы. `test_workflows.py` — исходные права, rate limit,
origin, отсутствие пароля в аудите. `test_ldap_contract.py` проверяет TLS CERT_REQUIRED,
read_only, отсутствие referrals, экранирование поиска и отказ без локального fallback.
Результат входит в свежий RC regression; [итоговая приёмка](FINAL_ACCEPTANCE_2026-10.md),
[полный pytest](evidence/release-rc/backend-final.txt).
Роль `manager` соответствует просмотру; отдельной роли viewer нет.

Это проверка контрактов LDAPS с подменённым транспортом. Настоящий bind к AD,
корпоративный CA, вложенные группы и централизованная ревокация остаются внешней проверкой.
Произвольный Authorization не отменяет CSRF. Исключение — распознанный действующий
Bearer машинной роли integrator. Чувствительные тела и credentials не включаются в аудит.

В Docker-контекст не включаются `.env` и `.env.*`. В примере конфигурации — только
плейсхолдеры; пароли тестов являются изолированными fixture, не доступом к стенду.
Устаревший публичный пароль убран из текущего README, но очистка старой Git-истории
и ротация действующих облачных credentials этим этапом не выполнялись.

RC cloud-образ выполняется uid 10001, не содержит backend/tests или .env;
изолированный запуск проверен с read-only filesystem и отдельным /tmp.
API не доверяет присланным proxy headers; внешняя платформа завершает HTTPS,
production cookies принудительно Secure. Нативная HTTPS-проверка подтвердила
CSRF 403, admin 403 для dispatcher, logout 200 → 401 и отсутствие cookie по HTTP:
[tls-security](evidence/release-rc/tls-security.json). Сертификат локальный тестовый;
публичный сертификат Railway отдельно проверен 19.10.2026: TLS1.3, доверенная цепочка,
Secure/HttpOnly/SameSite=strict, CSRF/401/403/истечение собственного QA-сеанса/logout,
прямой backend RBAC пяти ролей и аудит: [remote security](evidence/release-rc/remote/api-security.json).
Полный объём: [remote acceptance](REMOTE_RC_ACCEPTANCE_2026-10-19.md).

Защита от устаревших правок заявок действует при переданном expected_updated_at;
актуальный UI всегда передаёт имеющуюся версию. Legacy REST без версии сохраняет
совместимость и не получает такой гарантии. Пароли и сеансы не включены в evidence.
