# Как согласовывать функции в команде

Этот короткий пример показывает, как согласовать функцию до начала разработки. Пример — создание превентивной заявки по прогнозу высокого или критического риска.

## Пользовательский сценарий

Диспетчер открывает карточку объекта, проверяет информацию о риске и нажимает «Создать заявку». После отправки сервис показывает, что заявка создана, и сохраняет её статус.

## Что согласовать заранее

### Designer / Product

- Где находится кнопка создания заявки.
- Для каких уровней риска она доступна.
- Какие поля видит и заполняет диспетчер.
- Какие поля обязательны.
- Как выглядят состояния загрузки, успеха и ошибки.
- Что происходит, если заявка по этому прогнозу уже существует.
- Какие критерии означают, что функция готова для пользователя.

Предварительные данные заявки: объект и локация, тип и уровень риска, вероятность, краткое описание, приоритет и комментарий диспетчера.

### Backend

Backend определяет, какие данные принимает и возвращает сервис, и отвечает за серверную часть функции:

- проверяет обязательные поля и допустимые значения;
- сохраняет заявку и её статус в базе данных;
- не допускает повторного создания одной и той же заявки без понятного правила;
- возвращает понятные сообщения об ошибках;
- определяет, какие данные можно сохранять и показывать с учётом требований безопасности.

### Full-stack

Full-stack реализует пользовательский путь и связывает интерфейс с backend:

- добавляет кнопку и форму по согласованному макету;
- передаёт данные в backend;
- показывает состояния загрузки, успеха и ошибки;
- после успешного ответа отображает номер и статус заявки;
- проверяет функцию целиком — от карточки прогноза до сохранённой заявки.

## Как обсуждать функцию в чате

Перед разработкой отправляем в тему `🔌 Front + Back` короткое описание: название функции, пользовательский сценарий, решения Designer / Product, ожидаемые данные и поведение Backend, задачи Full-stack, владельца, срок и ссылку на макет или описание.

После обсуждения итоговое решение переносится в общий документ с решениями команды. Код пишется только после согласования сценария, данных и ответственных.

## Зачем это нужно

Без такого согласования Designer / Product может заложить один сценарий, Backend — другой формат данных, а Full-stack столкнётся с несовместимыми ожиданиями во время интеграции. Короткое описание заранее:

- даёт команде единое понимание результата;
- выявляет спорные места до написания кода;
- уменьшает количество переделок;
- упрощает проверку готовности функции;
- сохраняет решения, к которым можно вернуться позже.

Для небольшой функции достаточно одного сообщения по этому шаблону. Для крупной функции дополнительно нужны макет, описание данных и критерии приёмки.
