# ML-пакет LCT_ML_backend_v1.1

API читает сохранённые результаты. Модель запускается отдельным процессом Python 3.12.
Runtime перенесён из проверенной поставки без изменения признаков и параметров модели.
Контрольные суммы: ML_PACKAGE_SHA256.json. Переобучение при запуске не выполняется.

## Смысл результата

Активна только газовая модель: наблюдаемое пересечение 1 % CH4 снизу вверх в сутки
[D+2, D+3). Данные ограничены концом суток D по Europe/Moscow. Горизонт считается
от конца суток исходных данных, а не от фактического времени запоздавшего запуска.
Это experimental_shadow / proxy_score, не вероятность пожара и не подтверждённый инцидент.
Рекомендации имеют ручной справочный характер. Автоматические заявки и критические
уведомления отключены. Top-K по умолчанию 25, cooldown три дня.
Контекст ТО/поверки сохраняется и показывается; текущие тревоги он не подавляет.

Incident-head из поставки имеет label_source=stub. Производственный адаптер его
не загружает и не сохраняет его оценки. Настоящие прогнозы пожара, подтопления,
проникновения и отказов требуют подтверждённых меток и отдельной модели.

## Docker

1. Поместить gas_cross_v3_bundle.zip, gas_cross_v3_bundle.zip.sha256 и ACTIVE.json
   из поставки в models/bundles. Бинарные файлы игнорируются Git; итоговый архив их содержит.
2. Создать backend/.env из примера, задать собственные секреты, загрузить справочники
   и историю. Модель требует не менее 400 предшествующих суток; экспорт охватывает 430.
3. Из корня проекта:

```sh
docker compose --env-file backend/.env -f infra/compose.yaml --profile ml up --build -d
```

Служба ml проверяет завершение вчерашних суток каждые 300 секунд. Загрузчик данных
должен атомарно создать data/ml-ready/ready_YYYY-MM-DD.txt с единственной строкой
YYYY-MM-DD только после проверки полноты загрузки. Наличие файла — договор
с загрузчиком, не автоматическое доказательство полноты данных.

## Ручной запуск / внешняя история

Из backend в окружении с requirements-ml.txt:

```sh
python -m scripts.run_ml_daily --date 2026-07-31 --ready-marker /data/ready_2026-07-31.txt
python -m scripts.run_ml_daily --date 2026-07-31 --revision 2 --ready-marker /data/ready_2026-07-31.txt --journal /data/journal_2025.csv --journal /data/journal_2026.csv --catalogue /data/catalogue.csv
```

Внешние файлы задаются вместе: один или несколько --journal и --catalogue.
Справочник объектов и каналов должен уже быть в БД: неизвестные цели не сохраняются.
Пути внутри контейнера требуют отдельного read-only bind mount.
Старые пропущенные дни запускаются явно; планировщик не выполняет массовый backfill.

## Надёжность и история

БД выдаёт глобальную блокировку расчёта. Источник читается согласованным снимком.
Фиксируются SHA-256 входов, бандлов, runtime, конфигурации отбора и результата.
Одинаковый день/ревизия/вход повторно не создаёт записи. Изменённые входы требуют
новой ревизии. Старые результаты и решения диспетчера не удаляются.
Сбой после регистрации запуска отмечается failed с безопасным кодом ошибки.
Журнал запусков доступен в «Прогнозах» и GET /api/v1/predictions/runs.
Устаревшие результаты явно помечаются интерфейсом.

## Проверка

backend/scripts/check_ml_bundle.py запускает настоящую замороженную модель на
явно синтетических контрольных данных, только при ENVIRONMENT=test и пустом
журнале ML. Это проверка интеграции, не измерение точности модели. Проверяются
окно, происхождение, рекомендации, повторный запуск и отсутствие автоматических
действий. Тестовые данные и результаты нельзя переносить в рабочую БД.
