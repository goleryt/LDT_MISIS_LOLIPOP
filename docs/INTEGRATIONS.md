# Контракты интеграций

## Поток и синхронизация

POST /api/v1/integrations/{kind}; kind = telemetry, equipment, ods, work_status, weather.
Роль integrator (Bearer) либо admin (cookie+CSRF). Идентичность источника берётся из учётной записи.
Content-Type application/json: массив записей; application/xml: <records><record>...</record></records>.
Общие поля: external_id (непустая строка), observed_at (ISO 8601 с зоной). mock по умолчанию false; true разрешено только при явном включении тестового потока.
Повтор source/kind/external_id с тем же содержимым возвращает duplicates, с изменённым — 422. Для новой версии оборудования/статуса источник выдаёт новый ID сообщения.
Время поступления фиксируется отдельно от времени наблюдения. Ответ включает max_source_lag_seconds и within_300_seconds. Старые данные не маскируются как своевременные.

telemetry: известный channel_id, event_id, alarm, необязательный value. Это фактические показания; API не вычисляет риск. Тревожное новое событие создаёт уведомление, дубли не создают повтор.
equipment: object_id, name, опционально channel_id, sensor_type, system_type, tag, longitude/latitude. Объекты и каналы обновляются; перемещение канала между объектами отклоняется.
ods: description и метаданные; хранится неизменяемая запись журнала, доступная GET /integrations/records/ods.
work_status: известный request_id и допустимый переход status; обновляется локальная заявка с историей. Черновик внешний источник не подтверждает. Закрытые заявки не открываются. Внешняя система не меняется.
weather: longitude/latitude и хотя бы одно из temperature/humidity/precipitation/pressure; сохраняются наблюдения для будущей модели. Формат конкретной метеослужбы требует согласованного преобразования на границе источника.

## Read-only worker

python -m app.integration_worker. INTEGRATION_SOURCES_FILE указывает JSON по примеру infra/sources.example.json.
Worker обращается исключительно GET с query cursor. Источник возвращает:
{"records": [...], "next_cursor": "opaque-position"}.
TLS сертификаты проверяются; перенаправления выключены; bearer берётся из указанной переменной среды.
Курсор и данные сохраняются одной транзакцией. При ошибке курсор не продвигается, следующий цикл повторяет получение. Advisory lock допускает один активный worker в БД.
Опрос каждые 30 секунд по умолчанию. До пяти источников, ограничены размер ответа и время чтения. При сбое SLA не гарантируется — last_error виден в /integrations/status, необходим мониторинг.
Реальные URL, пагинация, внешние ID, маппинг реестров, права чтения и схема метеопровайдера согласуются с заказчиком.

## Тестовый источник

infra/compose.mock.yaml и infra/sources.mock.json подключают явный mock с объектом/датчиком 900001.
Запускать только на отдельной демонстрационной БД с ALLOW_MOCK_INGESTION=true.
Создаются только синтетические показания, помеченные mock; ML-модель, вероятности и inference не имитируются.
Mock содержит все пять видов источников. Для work_status передать `MOCK_REQUEST_ID` существующей тестовой заявки в состоянии `new`; без него источник возвращает пустой список статусов. Все внешние сообщения имеют отдельные ID. Запуск — только на изолированной тестовой БД, не на production.

## Файлы и геоданные

POST /imports/events?kind=events_journal|objects|channels — multipart file CSV/XLSX/JSON/XML; старый URL сохранён.
Заголовки событий: ид_события, ид_канала_данных, дата, время, тревожное, значение_датчика.
Объекты: ид_объект, иерархия_уровень, родитель, вид_объекта, диспетчерское_название_объекта.
Каналы: ид_канала_данных, тип_инж_системы, тип_датчика, тег_инженерной_системы, название_датчика, ид_объект.
Реестры обновляются по ключам. Для загрузки сначала импортировать объекты, затем каналы, затем события.
CSV/XLSX исторические дата/время — ISO (YYYY-MM-DD / HH:MM:SS), тревожное true/false/t/f; дополнительные форматы требуют предварительного отображения колонок.

PUT /geo/objects/{id}: {"geometry":{"type":"Point","coordinates":[lon,lat]}} либо {"wkt":"POINT (lon lat)"}.
GET /geo/objects: GeoJSON FeatureCollection с реальными точками и WKT в properties. Координаты — EPSG:4326, порядок долгота/широта.
Поддерживаются точки объектов; линии коллекторов и полигоны не подменяются точками и потребуют согласованной геосхемы заказчика.
Существующая карта остаётся схематической; объекты без координат имеют geometry_is_synthetic=true.

## Отчёты

GET /reports/observations или /reports/repairs: обязательные date_from/date_to (YYYY-MM-DD), format=json|xlsx|pdf. Наблюдения агрегируются по календарной дате источника; заявки выбираются по времени создания в UTC. Период — не более 367 календарных дней, лимит 5000 строк; при усечении сузить период. Для XLSX/PDF требуется авторизованная cookie, как и для JSON. Прогнозные метрики в эти отчёты не включаются.

## Проверяемый mock demo-flow

1. Создать отдельное окружение `ENVIRONMENT=test`, включить `ALLOW_MOCK_INGESTION=true`,
   создать dispatcher и обычную тестовую заявку, запомнить её ID.
2. Запустить `docker compose --env-file backend/.env -f infra/compose.yaml -f infra/compose.mock.yaml --profile integrations up -d --build` с `MOCK_REQUEST_ID` в окружении.
3. Проверить admin `/api/v1/operations/status`: пять источников, last_success, cursor,
   отсутствие ошибок. На карте появляется тестовый объект/канал 900001.
4. Открыть web-уведомление о фактической тревоге: переход к 900001/900001, история событий,
   индивидуальная отметка прочтения. Проверить запись операции в `/api/v1/audit`.
5. Проверить статус/историю указанной тестовой заявки. Остановить только собственные mock/worker,
   не удаляя БД и volumes.

Октябрьские тесты `test_integration_acceptance.py`: все пять видов, HTTP 500, timeout,
повтор, cursor, идемпотентность/upsert и per-user прочтение. Реальный GET worker
с mock HTTP-сервисом и Chrome UI проверен отдельно — [evidence](evidence/2026-10-16/mock-e2e.txt).
После ошибки следующий цикл продолжает работу; промышленные протоколы и SLA не доказаны mock-тестом.

RC worker проверяет, что JSON envelope является объектом и содержит next_cursor,
до обработки строк. Ошибочная форма, пропущенный cursor, invalid JSON и ConnectError
не сбрасывают ранее сохранённый cursor. Повтор и восстановление проверяются
`test_worker_malformed.py` в полном RC suite. Живой QA worker опросил все пять
источников, cursor=367, last_error=null: [snapshot](evidence/release-rc/live-integrations.txt).
У mock-work без MOCK_REQUEST_ID пустой набор: применение статуса к реальной локальной
заявке проверено контрактными тестами, не приписывается этому snapshot.
Воспроизводимый отдельный cloud QA: [DEPLOYMENT_RC](DEPLOYMENT_RC.md).

Импорт: при сбое строка реестра остаётся failed/processing, данные не фиксируются частично;
retry повторяет атомарную транзакцию. Матрица четырёх форматов и искусственно прерванной
загрузки — `test_import_acceptance.py`/`test_workflows.py`.
CSV/XLSX/JSON/XML доступны в UI выбора файла, не только через API.

В JSON/XLSX/PDF отчётах указаны источник, границы периода, часовой пояс, время формирования
и число строк. `/reports/repairs` сохранён для совместимости API; пользовательское название —
«История локальных заявок». Это не подтверждение ремонта во внешней системе.
